# MOMO-SAT OBC・データ処理系（C&DH）詳細設計書

文書番号: MOMO-SUB-OBC-001 / Rev A / 2026-07-11

## 1. 要求仕様の再掲

| ID | 要求 |
|---|---|
| DH-1 | 姿勢制御ループ 10 Hz、テレメトリ生成 1 Hz を処理 |
| DH-2 | 6 モード管理（自律・コマンド両方で遷移） |
| DH-3 | ウォッチドッグによる自律リセット、リセット後 SAFE 起動 |
| DH-4 | テレメトリ蓄積（1軌道分以上）と可視時一括再生 |
| PL-4/5 | RAW 6.4MB→JPEG 1MB 圧縮、8枚以上（64MB以上フラッシュ） |

## 2. ハードウェア構成

### 2.1 MCU 選定

STM32H750 相当（Arm Cortex-M7、480 MHz、ECC付き内蔵SRAM）を採用
（docs/02 記載）。

```
推定演算能力 ≈ 2.5 DMIPS/MHz × 480 MHz ≈ 1,200 DMIPS
```

姿勢決定・制御（TRIAD + クォータニオンPD）は数千命令オーダー/サイクルで
あり、10 Hz 実行でも負荷は 0.05 MIPS 程度（全体の 0.004%）に留まる
（§4 CPU バジェット参照）。480 MHz級 M7 コアは、ADCS制御ループに対しては
十分すぎる余裕があり、余剰能力を画像圧縮処理（JPEG エンコード）に
充当する設計とする。

### 2.2 メモリマップ

| 領域 | 容量 | 用途 |
|---|---|---|
| 内蔵 Flash（プログラム） | 128 KB〜2 MB（H750品種依存） | FSW バイナリ |
| 内蔵 SRAM（DTCM/ITCM/AXI SRAM合計） | 約 1 MB（ECC保護） | スタック、ADCS/TLMワーク領域、コマンドキュー |
| 外部 SDRAM（追加、本設計で新設） | 8 MB（SDRAM, FMCバス経由） | RAW画像バッファ（1枚6.4MB）、JPEG圧縮ワーク |
| 外部 NOR/NANDフラッシュ | 64 MB以上 | 画像蓄積ストレージ（PL-5要求） |
| TLMリングバッファ | 内蔵SRAM上に確保、約 64 KB | 1軌道分テレメトリ（§5） |

**外部SDRAM追加の根拠**: RAW画像 1 枚 6.4 MB は内蔵SRAM容量（約1MB）を
大きく超えるため、撮像→JPEG圧縮の中間バッファとして外部SDRAM
（8MB、FMCバス経由）を追加する。STM32H7シリーズはFMC/SDRAMコントローラを
内蔵しており、追加コストは基板配線・SDRAMチップ1個程度に留まる。

### 2.3 外部フラッシュ（画像格納）

```
必要容量 = MAX_STORED_IMAGES × IMAGE_SIZE_MB = 32 × 1.0 MB = 32 MB
```
搭載フラッシュ 64 MB に対し使用率 50%、PL-5要求（64MB以上）を満たし、
将来の圧縮率変動や複数解像度対応にもマージンを持つ。

### 2.4 ウォッチドッグ（WDT）

- **独立ウォッチドッグ（IWDG）**: MCU内蔵、独立クロック源で駆動。
  FSW メインループが一定時間（例: 2秒、10Hzループの20周期分）応答しない
  場合に MCU をリセット。
- **外付けウィンドウ型WDT**（docs/02記載）: MCU自体のクロック異常・
  電源異常等、内蔵WDTでは検出できない障害に対する二重防御。
  外付けWDTがタイムアウトすると、給電サイクラ（電源リセット）が
  作動し、MCUを完全に再起動する。
- **DH-3適合**: いずれのリセット経路でも、起動シーケンスは必ず
  Mode.SAFE から開始する（ICD docs/03 §2 記載のとおり）。

### 2.5 給電・I/F

| I/F | 接続機器 |
|---|---|
| I2C | IMU、磁気センサ、太陽センサ×6、温度センサ |
| SPI | RW×3、外部フラッシュ、カメラ（IMX547）、外部SDRAM制御と独立 |
| UART | GPS受信機、UHF/S帯トランシーバ |
| FMC（新設） | 外部SDRAM（画像バッファ） |

## 3. RTOSタスク設計

FreeRTOS（docs/02記載）ベースのタスク構成。優先度は数値が大きいほど高い
（FreeRTOS慣例に従う）。

| タスク | 周期 | 優先度 | 処理内容 |
|---|---|---|---|
| ADCS制御タスク | 10 Hz（0.1s） | 5（最高） | センサ取得、TRIAD/ジャイロ伝播、PD制御、RWトルク・MTQ指令出力 |
| ウォッチドッグ・キックタスク | 10 Hz | 5（最高、ADCSと同期） | IWDGリフレッシュ、健全性フラグ確認 |
| モード管理タスク | 10 Hz（ADCS後に実行） | 4 | モード状態機械の評価・遷移判定（DH-2） |
| コマンド処理タスク | イベント駆動（可視時のみ起床） | 3 | GroundCommand受信・解釈・実行キュー投入 |
| テレメトリ生成タスク | 1 Hz | 2 | Telemetry構造体更新、リングバッファ格納（DH-1） |
| ペイロード撮像タスク | イベント駆動（撮像トリガ時） | 3（撮像中は一時的に4へ昇格） | カメラトリガ、RAW取得、露光同期 |
| JPEG圧縮タスク | イベント駆動（撮像完了後） | 1（最低、バックグラウンド） | RAW→JPEG圧縮、フラッシュ書込み |
| ダウンリンク管理タスク | イベント駆動（可視時） | 2 | S帯送信制御、画像分割送信、ACK管理 |

### 3.1 優先度設計の考え方

- ADCS制御とWDTキックを最優先とすることで、他タスクの遅延・ハングが
  発生してもレート制御の安全性（AD-3: 撮像中レート0.05°/s以下）と
  WDTリセット回避を保証する。
- JPEG圧縮は最低優先度のバックグラウンドタスクとし、ADCS制御に一切
  割り込ませない（プリエンプティブスケジューリングにより自動的に
  中断・再開される設計）。
- コマンド処理・ダウンリンクはイベント駆動（地上局可視時のみ起床）とし、
  非可視時はCPU負荷ゼロ。

## 4. CPU・メモリバジェット

### 4.1 CPU バジェット

| タスク | 処理量（概算） | 頻度 | 負荷 [MIPS] |
|---|---|---|---|
| ADCS制御 | 命令数 ≈5,000（クォータニオン演算・TRIAD・PD則） | 10 Hz | 0.05 |
| テレメトリ生成 | 命令数 ≈2,000 | 1 Hz | 0.002 |
| JPEG圧縮 | 80 cycles/pixel × 2472×2064 px ≈ 4.08e8 cycles | 撮像毎（4回/日） | 分散処理で常時負荷は無視可 |
| **合計常時負荷** | | | **≈0.05 MIPS** |

CPU能力 1,200 DMIPS に対し常時負荷は 0.05 MIPS（0.004%）と極めて小さく、
DH-1要求（10Hz ADCS、1Hz TLM処理）に対し十分な余裕がある。

JPEG圧縮の所要時間：
```
t_jpeg = cycles / f_cpu = 4.08e8 / 480e6 ≈ 0.85 s/枚
```
撮像1枚あたり0.85秒の圧縮時間は、バックグラウンド低優先度タスクとして
数秒〜十数秒の許容時間内で十分完了する（撮像間隔は分オーダー）。

### 4.2 メモリバジェット

```
RAWバッファ: 6.4 MB × 1（同時処理1枚）= 6.4 MB（外部SDRAM上）
JPEG圧縮ワーク: 概算 1〜2 MB（外部SDRAM上、RAWバッファと共用領域）
画像蓄積: 32枚 × 1.0 MB = 32 MB（外部フラッシュ、64MB中50%使用）
TLMリングバッファ: 1軌道分（94.5分 = 5,670秒）× 1Hz × 各サンプル約12B
                  ≈ 5,670 × 12B ≈ 68 KB（内蔵SRAM上、DH-4要求適合）
```

内蔵SRAM（約1MB）に対し、TLMバッファ（68KB）・スタック・ワーク変数の
合計使用量は数百KB以内に収まり、十分な余裕を残す。

## 5. FDIR設計（フォルト検知→SAFE遷移）

### 5.1 フォルト検知項目

| フォルト種別 | 検知条件 | fault_flags ビット |
|---|---|---|
| ジャイロ異常 | センサ値が物理的上限（例: ±100°/s）を超過、または一定時間更新なし | bit 0 |
| 磁気センサ異常 | 値が地磁気想定レンジ外（例: >1e-3 T）、または欠測継続 | bit 1 |
| 太陽センサ異常 | 全チャンネル同時異常値（食判定と矛盾する継続無効） | bit 2 |
| RW過速度/過熱 | wheel_speeds が物理上限相当を超過 | bit 3 |
| RW角運動量飽和継続 | `RW_MAX_MOMENTUM`近傍で脱飽和が機能せず継続 | bit 4 |
| バッテリ電圧異常 | battery_voltage が許容範囲外（低電圧保護） | bit 5 |
| バッテリ温度異常 | battery_temp が −20℃以下または+60℃以上（TH-1逸脱の予兆） | bit 6 |
| SoC低下 | battery_soc < 0.30（EP-4、既存の自律SAFE遷移条件） | bit 7 |
| 姿勢決定ロスト | TRIAD/ジャイロ推定が長時間未更新（食超過等） | bit 8 |
| 通信途絶 | 想定パスでgs_visibleが得られない状態が規定回数継続 | bit 9 |
| ウォッチドッグ復帰 | 直前起動がWDTリセット由来（DH-3） | bit 10 |
| ペイロード異常 | カメラI/F応答なし、フラッシュ書込みエラー | bit 11 |
| 予約 | 拡張用 | bit 12〜31 |

`fault_flags` は `Telemetry.fault_flags`（`common/types.py`定義）に
そのままビット単位でマッピングし、0=正常を維持する。

### 5.2 検知→SAFE遷移ロジック

```
[10Hz ADCS制御タスク内で毎周期評価]
  1. センサ・アクチュエータ値を物理レンジチェック
  2. 異常検知時、対応する fault_flags ビットをセット
  3. bit 0-6（センサ・アクチュエータ致命的異常）または bit 7（SoC低下、
     既存EP-4条件）が立った場合、モード管理タスクへ SAFE遷移要求を送信
  4. モード管理タスクは要求を受け、現在モードに関わらず即座に
     Mode.SAFEへ遷移（DH-2「どのモードからも」に対応）
  5. SAFE遷移時、ペイロード電源OFF・送信機OFF（負荷遮断）、
     MTQ B-dot制御のみ継続
```

### 5.3 復旧条件

- SoC低下によるSAFE遷移（bit 7）: SoC ≥ 0.50 まで回復でヒステリシス解除、
  地上コマンドまたは自律で DETUMBLE/SUNPOINTへ復帰可能。
- センサ異常（bit 0-2）: 一定時間（例: 60秒）正常値が継続すればフラグ
  クリア、地上コマンドによる明示的な復帰確認を推奨（自動復帰は
  誤判定リスクがあるため、姿勢系異常は地上判断を基本とする）。
- WDTリセット由来（bit 10）: 起動後SAFEで待機し、地上局からのテレメトリ
  確認後、コマンドで復帰させる運用（DH-3の「リセット後SAFE起動」を
  安全側の既定動作とする）。
