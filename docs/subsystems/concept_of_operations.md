# MOMO-SAT 運用コンセプト（ConOps）

文書番号: MOMO-SUB-OPS-001 / Rev A / 2026-07-11
上位文書: docs/01_mission_requirements.md, docs/02_system_architecture.md, docs/03_software_icd.md

## 1. 運用フェーズ概要

```
放出 → 初期運用（デタンブル→チェックアウト） → 定常運用（撮像・ダウンリンクサイクル）
                                                    ↕（異常検知）
                                              異常時運用（SAFE遷移・復旧）
```

## 2. 初期運用（LEOP: Launch and Early Orbit Phase）

### 2.1 タイムライン

| 時刻 | イベント | モード遷移 | 備考 |
|---|---|---|---|
| T+0 | 放出（分離コネクタ解放） | 起動→SAFE | 初期姿勢はタンブリング状態（〜10°/s、AD-4想定初期値） |
| T+0〜T+60s | 起動シーケンス、センサ初期化、WDT有効化 | SAFE | 全ペイロード・送信機OFF（負荷遮断） |
| T+60s | 自律遷移 | SAFE→DETUMBLE | ICD docs/03 §2「起動後60sの自律遷移」 |
| T+60s〜T+約220s | B-dotデタンブル実行 | DETUMBLE | adcs.md §5.1: 理論所要時間約96s（10°/s→0.5°/s）+ 60s継続確認 |
| T+約220s | レート判定成立（\|ω\|<0.5°/s 60s継続） | DETUMBLE→SUNPOINT | 自律遷移（ICD docs/03 §5） |
| T+約220s〜 | 太陽捕捉・充電開始 | SUNPOINT | RW3軸で−Z面を太陽方向へ |

デタンブル所要時間は理論値約96秒（adcs.md §5.1）にレート継続確認60秒を
加え、AD-4要求（2軌道 = 188.9分以内）に対し**大幅なマージン（2軌道の
約2%）**で完了する。

### 2.2 チェックアウト（初回可視パス以降）

1. **初回可視パス確立**: 放出後、地上局（東京局）の最初の可視パスで
   UHF回線（CM-1）を確立し、テレメトリ受信によりSAFE/DETUMBLE/SUNPOINT
   遷移の実績を確認する。
2. **バスサブシステム健全性確認**: バッテリSoC・電圧・温度、姿勢決定値
   （q_est, omega_est）、fault_flags（obc_cdh.md §5）をテレメトリで確認。
3. **ADCS精度確認**: SUNPOINT安定後、pointing_error_degがAD-2相当
   （±0.5°オーダー）に収束していることを確認。
4. **ペイロード疎通確認**: 地上コマンドでNADIR_IMAGINGへ遷移させ、
   試験的に1枚撮像・ダウンリンクを実施し、撮像系・通信系の end-to-end
   動作を確認する。
5. **チェックアウト完了判定**: 上記1〜4が全て正常であれば定常運用へ移行。
   想定所要期間: 放出後2〜3日（可視パス4〜6回/日 × 数日分の確認機会）。

## 3. 定常運用（1日サイクル）

### 3.1 運用サイクル概要

MR-2（1日4枚以上取得・伝送）、MR-3（指定ターゲット撮像）、
MR-4（48時間以内ダウンリンク）を満たす日次運用サイクル：

```
[地上] 撮像計画立案（ターゲット選定、可視パス時刻算出）
   ↓（可視パスでコマンドアップリンク）
[衛星] SUNPOINT（待機・充電） → NADIR_IMAGING/TARGET_IMAGING（撮像）
   → SUNPOINT（自動復帰） → DOWNLINK（可視パスで送信） → SUNPOINT
```

### 3.2 撮像計画からダウンリンクまでの具体的コマンド列

地上局（東京局）は可視パス中のみ `GroundCommand`（docs/03 §2, ICD）を
衛星へ送信できる。以下は1日の代表的な運用シーケンス例。

**パス1（朝、直下点撮像）**:
```python
# 1. 直下撮像コマンド送信（NADIR_IMAGINGへ遷移、2枚撮像）
GroundCommand(type="IMAGE_NADIR", params={"count": 2})
```
→ 衛星はNADIR_IMAGINGへ遷移し、指向誤差<0.5°かつレート<0.05°/sの
条件（ICD docs/03 §5、AD-2/AD-3相当）が満たされ次第、2枚撮像。
完了後、SUNPOINTへ自動復帰。

**パス2（昼、指定ターゲット撮像、MR-3対応）**:
```python
# 2. 指定地点撮像コマンド（緯度経度指定、TARGET_IMAGINGへ遷移）
GroundCommand(type="IMAGE_TARGET", params={"lat_deg": 35.36, "lon_deg": 138.73})
# 例: 富士山周辺を指定ターゲットとする場合
```
→ 衛星軌道が当該地点の直下点±100km（MR-3）を通過するタイミングで
撮像。TARGET_IMAGINGはNADIR_IMAGINGと同様、条件成立後に自動撮像し
SUNPOINTへ復帰。

**パス3（夕、蓄積画像のダウンリンク）**:
```python
# 3. ダウンリンク開始コマンド
GroundCommand(type="DOWNLINK", params={})
```
→ 衛星はDOWNLINKモードへ遷移、−Z面を地上局方向（天頂）へ指向し、
可視継続中（gs_visible=True）tx_active=Trueで蓄積画像を順次送信。
comm.md §6.3の試算どおり、1パス（平均5〜6分）で約3.75MB
（3.75枚相当）を伝送可能であり、当日撮像分（4枚=4MB）は
1〜2パスで完全にダウンリンクされる。全画像送信完了で
SUNPOINTへ自動復帰。

**必要に応じたモード確認・強制復帰コマンド**:
```python
# 4. 現在モード確認のためテレメトリ取得は毎パス自動（get_telemetry）
# 5. 異常時の明示的SAFE復帰（4章参照）
GroundCommand(type="SET_MODE", params={"mode": Mode.SAFE})
# 6. リセット指示（フォルト解除後の再初期化）
GroundCommand(type="RESET", params={})
```

### 3.3 日次データ収支（comm.md §6より再掲）

```
撮像: 4枚/日 × 1.0MB(圧縮後) = 4.0 MB/日
ダウンリンク所要: 4.0MB ÷ 0.0125MB/s = 320秒（1パス容量3.75MBに近く、
                  実運用では2パスに分割される場合もある）
可視パス: 4〜6回/日（comm.md §5.3）
```

1日で撮像4枚・ダウンリンク4枚を、4〜6回の可視パスのうち2〜3パスに
割り当てることで、MR-2・MR-4を安定して満たす運用が可能。

### 3.4 撮像計画立案の考慮事項（地上系）

- 軌道予報（TLE等）から当日の直下点通過ターゲット候補と、指定ターゲット
  （緯度経度、MR-3）の通過時刻・直下距離を事前算出。
- 日照区間での撮像を基本とする（adcs.md §7.6: 食中は太陽センサ利用不可
  でTRIAD補正が働かず姿勢決定精度AD-1が劣化するため）。
- 撮像コマンドは可視パス中にアップリンクし、衛星は次の該当ジオメトリ
  （直下点通過またはターゲット直下±100km）まで待機してから自動撮像
  する設計（ICD docs/03 §5参照）。

## 4. 異常時運用

### 4.1 SAFE遷移条件（自律）

| 条件 | 説明 |
|---|---|
| バッテリSoC < 30%（EP-4） | 電力枯渇の予兆、既存の自律SAFE遷移条件 |
| フォルト検知（obc_cdh.md §5） | センサ異常、RW異常、姿勢決定ロスト等、fault_flagsに応じてどのモードからもSAFEへ |
| ウォッチドッグリセット（DH-3） | MCUリセット後は必ずSAFE起動 |

SAFE遷移時の衛星挙動: 全ペイロード・送信機電源OFF（負荷遮断）、
MTQによるB-dot姿勢安定制御のみ継続、最低限のテレメトリ生成を維持。

### 4.2 地上からの異常判断・介入

1. **テレメトリ監視**: 毎可視パスでmode, battery_soc, battery_temp,
   fault_flags, pointing_error_degを確認。
2. **SAFE遷移検知**: テレメトリのmodeがSAFEであることを確認したら、
   fault_flagsのビットパターンから原因を切り分け（obc_cdh.md §5.1表）。
3. **原因別対応**:
   - SoC低下（bit 7）: 太陽電池発生電力・姿勢履歴を確認し、
     自然回復（SUNPOINT自律運用でのSoC上昇、EP-4ヒステリシス解除
     SoC≥50%）を待つ。長期化する場合は太陽電池異常を疑い、
     詳細診断コマンドで個別面の発生電力を確認。
   - センサ異常（bit 0-2）: 該当センサの単独異常か複合異常かを確認。
     単独異常であれば縮退運用（例: 磁気センサのみでのB-dot継続）を
     地上コマンドで指示。
   - RW異常（bit 3-4）: RW脱飽和状況を確認し、MTQのみによる姿勢維持
     （縮退SUNPOINT相当）への切替を検討。
   - WDTリセット由来（bit 10）: FSWログ・直前テレメトリを確認し、
     再発しないことを確認した上で復帰コマンドを送信。

### 4.3 復旧手順（代表例）

```python
# Step 1: 状態確認後、フォルトクリアを確認してからDETUMBLE経由で復帰
GroundCommand(type="SET_MODE", params={"mode": Mode.DETUMBLE})
# Step 2: レート減衰確認後、自律的にSUNPOINTへ遷移することを
#         次パスのテレメトリ（mode, omega_est）で確認
# Step 3: 問題が解消しない場合、明示的リセットで再初期化
GroundCommand(type="RESET", params={})
# → SAFEへ強制復帰し、起動シーケンスを再実行
```

- 復旧はコマンドによる段階的モード遷移（SAFE→DETUMBLE→SUNPOINT）を
  基本とし、いきなり撮像・ダウンリンクモードへ復帰させず、
  バス機能の健全性を都度確認しながら進める。
- 同一フォルトが3回以上（3日以上）繰り返される場合は、当該サブシステム
  を運用上「使用不可」と判断し、縮退運用計画（例: 撮像頻度を落として
  電力マージンを確保）へ切り替える。

### 4.4 異常時運用まとめ

| フェーズ | 対応方針 |
|---|---|
| 検知 | fault_flags・テレメトリ監視、SAFE遷移の自動検知 |
| 診断 | ビットパターンから原因切り分け、必要に応じ詳細テレメトリ取得 |
| 復旧 | 段階的モード遷移（SAFE→DETUMBLE→SUNPOINT）、都度健全性確認 |
| 縮退運用 | 恒常的な異常時は機能限定運用へ切替、ミッション達成を優先 |

## 5. 運用体制まとめ

| 項目 | 内容 |
|---|---|
| 地上局 | 東京局（35.68°N, 139.77°E）、仰角マスク10° |
| 可視パス頻度 | 約4〜6回/日（comm.md §5.3） |
| 定常運用サイクル | 撮像（NADIR/TARGET_IMAGING）→SUNPOINT自動復帰→DOWNLINK→SUNPOINT |
| 初期運用所要期間 | デタンブル約220秒（AD-4要求2軌道に対し大幅マージン）、チェックアウト2〜3日 |
| 異常時対応 | 自律SAFE遷移＋地上診断・段階的復旧、縮退運用オプションを保持 |
